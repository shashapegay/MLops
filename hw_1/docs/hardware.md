# Hardware Report

## 1. Environment

Работа выполнялась на компьютере под управлением **Windows** с использованием **CPU** для запуска модели.

Параметры запуска:

* **Operating system:** Windows
* **Device:** CPU
* **Model:** `Qwen/Qwen3-0.6B`
* **Dtype:** `bfloat16`
* **Python:** 3.12
* **Package manager:** `uv`

Модель запускалась локально, без использования GPU.

## 2. Benchmark results

Для оценки производительности были измерены три отдельные характеристики: время загрузки модели, скорость генерации токенов и максимальное потребление оперативной памяти.

Полученные результаты:

| Metric              |            Result |
| ------------------- | ----------------: |
| Model               | `Qwen/Qwen3-0.6B` |
| Device              |             `cpu` |
| Dtype               |        `bfloat16` |
| Model load time     |         `5.18 sec` |
| Tokens/sec (median) |           `8.02` |
| Tokens/sec, run 1   |           `7.96` |
| Tokens/sec, run 2   |           `8.02` |
| Tokens/sec, run 3   |           `8.02` |
| Peak RSS            |       `2716.6 MB` |

Скорость генерации составила **8.02 токена/с по медиане** трёх измерений.

Отдельные результаты трёх запусков:

* первый запуск: **7.96 tokens/sec**;
* второй запуск: **8.02 tokens/sec**;
* третий запуск: **8.02 tokens/sec**.

Таким образом, результаты находятся в достаточно близком диапазоне, без существенных выбросов.

## 3. Hardware profile

Для выполнения работы был выбран профиль **CPU-only**.

Причина выбора заключается в том, что benchmark выполнялся на Windows с использованием центрального процессора без GPU. Модель `Qwen/Qwen3-0.6B` имеет небольшой размер и может запускаться локально на CPU, поэтому такой вариант подходит для проверки работоспособности окружения и выполнения первого inference.

При этом использование `bfloat16` на CPU может быть менее производительным, чем запуск модели на подходящем GPU. Полученная скорость генерации — **8.02 tokens/sec** — характеризует именно текущую конфигурацию CPU + `bfloat16`.

## 4. Known defects in the original project

В исходной версии проекта были обнаружены четыре намеренных дефекта.

### 4.1. Hardcoded model name

**Problem:**
Название модели было записано непосредственно в исходном коде в нескольких местах проекта.

**Symptom:**
При необходимости заменить модель приходилось изменять исходный код. Это нарушает принцип конфигурации через `params.yaml` и может привести к тому, что разные части проекта будут использовать разные модели.

**Fix:**
Название модели было вынесено в `params.yaml`:

```yaml
model:
  name: "Qwen/Qwen3-0.6B"
```

Исходный код получает название модели из конфигурации через `src/config.py`.

Таким образом, модель можно изменить в одном месте — в `params.yaml` — без изменения Python-кода.

### 4.2. Unpinned dependencies

**Problem:**
Зависимости проекта не были зафиксированы конкретными версиями, а lock-файл `uv.lock` отсутствовал или не обеспечивал воспроизводимое окружение.

**Symptom:**
При установке проекта в другое время или на другом компьютере могли быть установлены другие версии зависимостей. Это может привести к различиям в поведении программы и проблемам совместимости.

**Fix:**
Для управления зависимостями используется `uv`. Зависимости фиксируются через lock-файл:

```text
uv.lock
```

Lock-файл должен быть добавлен в репозиторий, чтобы установка зависимостей была воспроизводимой.

### 4.3. Benchmark смешивал время загрузки модели и генерации

**Problem:**
В исходном benchmark время загрузки модели и время генерации не были корректно разделены.

**Symptom:**
Время, необходимое для загрузки модели, могло влиять на измерение скорости генерации. В результате полученное значение tokens/sec не характеризовало только производительность генерации.

**Fix:**
Benchmark разделён на отдельные этапы:

1. загрузка модели;
2. warm-up;
3. измерение генерации;
4. расчёт tokens/sec;
5. измерение peak RSS.

Время загрузки модели измеряется отдельно от времени генерации. Для итоговой скорости генерации используются отдельные измерения после warm-up, а итоговым значением является медиана.

### 4.4. Невоспроизводимая генерация

**Problem:**
В исходной конфигурации генерация использовала sampling и не обеспечивала полностью детерминированный результат.

**Symptom:**
Повторный запуск с одним и тем же prompt мог приводить к разным результатам.

**Fix:**
В `params.yaml` установлены параметры:

```yaml
generate:
  temperature: 0.0
  seed: 42
  enable_thinking: false
```

При `temperature: 0.0` генерация становится детерминированной. Использование фиксированного seed дополнительно обеспечивает воспроизводимость эксперимента.

## 5. Reproducibility

Конфигурация эксперимента хранится в `params.yaml`, поэтому основные параметры запуска не задаются непосредственно в исходном коде.

Текущая конфигурация модели:

```yaml
model:
  name: "Qwen/Qwen3-0.6B"
  dtype: "bfloat16"
  device: "auto"
```

Параметры генерации:

```yaml
generate:
  max_new_tokens: 200
  temperature: 0.0
  seed: 42
  enable_thinking: false
```

Для benchmark используются warm-up и три измерительных запуска. Итоговая скорость генерации рассчитывается как медиана результатов:

```text
7.96, 8.02, 8.02 tokens/sec

median = 8.02 tokens/sec
```

## 6. Conclusion

В результате работы окружение было настроено для запуска языковой модели `Qwen/Qwen3-0.6B` на CPU под Windows.

Benchmark показал:

* **model load time:** 5.18 sec;
* **generation speed:** 8.02 tokens/sec (median);
* **peak RSS:** 2716.6 MB.

Используемый hardware profile — **CPU-only**.

Также были исправлены основные дефекты исходного проекта: название модели вынесено в конфигурацию, зависимости зафиксированы с помощью `uv.lock`, время загрузки модели отделено от измерения генерации, а генерация сделана воспроизводимой с помощью фиксированных параметров.

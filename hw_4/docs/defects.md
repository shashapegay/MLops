# Разбор дефектов

## 1. Prompt попадал в loss

В исходной реализации граница между prompt и ответом ассистента определялась недостаточно надёжно. Для обучения нужно передавать модели всю последовательность, но вычислять loss только по токенам последней реплики ассистента. Токены prompt должны иметь значение `-100` в `labels`, потому что `CrossEntropyLoss` с таким `ignore_index` не учитывает эти позиции при вычислении ошибки.

Проблема особенно заметна, если пытаться определить границу только по длине отдельно токенизированного prompt. BPE-токенизатор может по-разному разбить строку, когда начало ответа присоединяется к последнему фрагменту prompt. Поэтому простое сравнение количества токенов не всегда даёт устойчивую границу.

Исправление состоит в том, что полный текст и текст prompt строятся одним и тем же `apply_chat_template`. Затем prompt токенизируется отдельно и сначала проверяется, совпадает ли его последовательность токенов с началом полной последовательности. Если это невозможно из-за BPE-склейки, используется `return_offsets_mapping=True`: граница определяется по символам, а токен, пересекающий границу, остаётся замаскированным. Это безопаснее, чем случайно включить часть prompt в обучающий сигнал.

## 2. Train и inference использовали разные шаблоны

Вторая ошибка возникает, когда строка для обучения собирается одним способом, а строка для генерации — другим. Для chat-моделей формат ролей, специальные токены, разделители и окончание сообщения являются частью входа модели. Ручная конкатенация строк легко приводит к расхождению между train и inference.

Правильная схема — использовать `tokenizer.apply_chat_template` в одном общем модуле. Для обучения передаётся полный диалог без последнего generation prompt, а для inference используется тот же шаблон с `add_generation_prompt=True`. При этом inference-строка должна быть побайтовым префиксом train-строки: после неё обучение просто продолжает последовательность токенами ответа ассистента.

В проекте это исправлено в `src/prompt.py`. В нём нет ручной записи специальных токенов ролей. Параметр `enable_thinking` также передаётся через конфигурацию, чтобы режим шаблона был одинаковым в обоих сценариях. Такая организация уменьшает риск того, что изменение шаблона модели потребует одновременно исправлять несколько мест в коде.

## 3. Padding выполнялся справа

Для decoder-only модели положение токенов внутри батча имеет значение. При динамическом выравнивании последовательностей padding должен находиться слева, чтобы последние реальные токены всех примеров были выровнены по одной позиции. Это особенно важно при использовании causal language model и при подготовке батчей разной длины.

Дополнительная ошибка возникает, если оставить обычные значения labels на padding-позициях. Тогда модель получает обучающий сигнал на искусственных pad-токенах, которые не являются частью исходного текста. Такие позиции должны иметь `-100` в `labels`, а `attention_mask` должен содержать ноль на padding и единицу на настоящих токенах.

В проекте направление padding вынесено в `params.yaml` и установлено в `left`. Коллатор использует это значение, а labels на добавленных padding-позициях заполняются `-100`. Таким образом, padding влияет только на выравнивание батча и не превращается в дополнительную задачу для модели.

## 4. Обрезка по max_seq_len не контролировалась

Последовательность длиннее `max_seq_len` нельзя целиком передать модели. Если просто обрезать её без статистики, можно незаметно потерять значительную часть ответов. Особенно плохо, если truncation чаще всего происходит именно на длинных и информативных примерах: средняя длина может выглядеть нормально, хотя хвост распределения будет систематически теряться.

Исправление состоит в подсчёте количества и доли обрезанных примеров до их последующей фильтрации. В проекте сохраняются `full_len`, `truncated`, количество supervised-токенов и статистика длин. Доля обрезанных записывается в `metrics/tokenize.json`, а в отчёте отображается отдельно для train и validation.

Есть ещё важная деталь: если после обрезки ответ ассистента полностью исчез, такой пример нельзя оставлять в обучающем наборе — в нём не останется ни одной позиции для loss. Поэтому такие примеры учитываются в статистике, но исключаются из сохранённых обучающих примеров. Порог предупреждения задан в `params.yaml`; это позволяет контролировать качество препроцессинга, не пряча проблему внутри кода.

## 5. Почему нужна отдельная проверка границы BPE

Граница между prompt и ответом является не только строковой, но и токенизационной проблемой. Один BPE-токен может содержать символы по обе стороны границы, поэтому границу нельзя надёжно получать только сравнением строк или только длиной prompt в токенах.

В текущей реализации сначала используется быстрый и точный путь: токены prompt сравниваются с началом полной последовательности. Если они не совпадают, используются символьные offsets полного текста. Первый токен, который начинается не раньше конца prompt, считается началом supervised-части.

Такой fallback специально консервативен: если один токен пересекает границу, он остаётся замаскированным. Потеря одного токена ответа предпочтительнее ситуации, когда в loss случайно попадает часть пользовательского prompt. Метрика `bpe_boundary_fallback` позволяет увидеть, насколько часто пришлось использовать этот запасной путь.

## Итог

После исправлений стадия `tokenize` должна выполнять все основные обязанности препроцессинга: единообразно строить chat-template, маскировать prompt, корректно обрабатывать BPE-границу, сохранять левый padding, контролировать truncation и писать воспроизводимые метрики. Конфигурация этих параметров находится в `params.yaml`, а зависимости стадии перечислены в `dvc.yaml`, поэтому изменение кода или параметров приводит к корректному пересчёту артефактов.
